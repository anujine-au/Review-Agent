# Prompt: Тайлан хянуулах → Захирлын батлалт → Засвар → Хувилбар → Эцсийн тайлан

> Энэ prompt-ийг «Review Agent» хавтаст Claude Code-д өгнө. Шинээр систем бүтээх биш, **одоо байгаа** `server/` + `web/index.html`-ийг өргөтгөнө.

---

## 0. Чиний үүрэг ба хязгаар

Чи «Review Agent» системийн хөгжүүлэгч. Эхлээд `CLAUDE.md`, `README.md`, `requirements/REVIEW_CONDITIONS_DRAFT.md`, `server/server.js`, `server/users.js`, `server/originals.js`, `server/standard.js`, `server/export.js`-ийг уншиж, одоогийн бүтцийг ойлго.

- **Код бичихээс өмнө** доорх §8-ын төлөвлөгөөг (өөрчлөх файл, шинэ endpoint, өгөгдлийн бүтэц, эрсдэл) надад харуулж зөвшөөрөл ав.
- Гадны npm сан нэмэхгүй (одоогийнх шиг зөвхөн Node.js built-in).
- Маск, `mask_map.json`, sandbox, EFS, retention, audit log, SP-118-04 логикийг **сулруулахгүй**.
- Одоо ажиллаж буй review, recheck (M14), finalize, `/review-audit`, `/publish-docs`, `/sync-docs`-ийг эвдэхгүй.
- Хуучин job-ууд (`jobs/*`) шинэ төлөвгүй байсан ч алдаагүй нээгдэх ёстой (migration эсвэл default утга).

## 1. Одоо байгаа зүйл (дахин бүү хий)

| Боломж | Хаана |
|---|---|
| Role: `admin`, `cae` (ДАГ-ын захирал), `reviewer`, `auditor`, `viewer` | `users.js` ROLES/PERMS |
| AI review, verdict (READY / READY_WITH_FIXES / NOT_READY / ESCALATE) | `runner.js`, `standard.js` |
| Захирлын санал бүрийн шийдвэр APPROVED / EDITED / REJECTED | `POST/PATCH /api/jobs/:id/decisions` |
| Гараар нэмэх тэмдэглэл (MAN-xxx) | `/comments` |
| Дахин хяналт: `parent_id` + `round` гинж (C1, C2, …), M14 recheck | `POST /api/jobs` + `recheck.json` |
| Хувилбар бүрийн эх файл (sha256-тай) | `originals.js`, `GET /originals` |
| Эцсийн батлалт: RPT-174-YYYY-NNN, архив 10 жил | `POST /finalize` |

## 2. Олдсон зөрүү (заавал засна)

1. **Батлахаас өмнө аудиторт харагддаг.** Захирал саналыг APPROVED болгомогц `filterForAuditor` аудиторт шууд харуулдаг. Мөн `GET /api/jobs/:id` нь `decisions`, `verdict`, `r1..r4`, `events`-ийг аудиторт ч буцаадаг. → «Батлаад илгээх» товч дарагдах хүртэл аудиторт **юу ч** харагдах ёсгүй.
2. **«Батлаад илгээх» (release) үйлдэл байхгүй.** Шийдвэр бүр нэг бүрчлэн хадгалагдаж, нэг мөр илгээгдэх агшин байхгүй.
3. **Ахлах аудитор гэсэн role байхгүй.** Мөн job-ийг зөвхөн `created_by` эзэмшдэг, багийн гишүүд хамт харах боломжгүй.
4. **Мэдэгдэл байхгүй.** Feedback илгээгдсэн, дахин хянуулах хүсэлт ирсэн гэдгийг хүн мэдэхгүй.
5. **Google Docs линк хувилбарлагддаггүй.** Линкийн агуулга дараа нь өөрчлөгдөнө, тиймээс тухайн агшны хуулбар хадгалагдах ёстой.
6. **Эцсийн «цэвэр» тайлан татах товч байхгүй.** `finalize` нь review-ийн экспортыг архивладаг, харин аудиторын сүүлийн хувилбарын тайланг захиралд нэг товчоор өгдөггүй.

## 3. Оролцогч ба эрх

| Role | Шинэ / одоо | Эрх |
|---|---|---|
| `lead_auditor` — Ахлах аудитор | **шинэ** | Хүсэлт үүсгэх, файл/линк оруулах, дахин хянуулах; багийнхаа job-ийг харах; release болсон feedback-ийг харах |
| `auditor` — Дотоод аудитор | одоо | Дээрхтэй адил, гэхдээ зөвхөн өөрийн оролцсон job |
| `cae` — Газрын захирал | одоо | Бүх job; санал шийдвэрлэх; **Батлаад илгээх**; эцэслэн батлах; эцсийн тайлан татах |
| `reviewer` | одоо | Захирлын эрх шилжүүлсэн үед санал шийдвэрлэх; release / finalize хийхгүй |
| `viewer`, `admin` | одоо | Өөрчлөхгүй |

- Job-д `team: [username…]` талбар нэм. Хүсэлт үүсгэхэд ахлах аудитор болон аудиторыг сонгоно. `canSeeJob` = `created_by` эсвэл `team`-д байгаа.
- Бэлтгэгч ≠ Хянагч (DOC-1917 §9) дүрэм хэвээр: багийн гишүүн өөрийн тайланг шийдвэрлэж, release хийж чадахгүй.
- PERMS-д нэм: `job.release: ['cae']`, `job.downloadFinal: ['cae', 'admin']`. `lead_auditor`-ыг `job.create`-д нэм.

## 4. Ажлын урсгал (төлөвийн машин)

`job.json`-д `workflow` талбар нэм. Одоогийн `state.status` (extracting/running/done…) нь AI-ийн гүйцэтгэлийн төлөв хэвээр үлдэнэ, `workflow` нь бизнесийн төлөв.

```
DRAFT ──Хянуулах──▶ SUBMITTED ──AI дуусав──▶ CAE_REVIEW ──Батлаад илгээх──▶ RETURNED
                                                │                              │
                                                │                   аудитор засаад дахин upload
                                                │                              ▼
                                                │                    RESUBMITTED (v2, v3…) ──▶ CAE_REVIEW …
                                                └──Эцэслэн батлах──▶ APPROVED_FINAL (түгжигдэнэ)
```

| Шилжилт | Хэн | Нөхцөл | Үр дүн |
|---|---|---|---|
| DRAFT → SUBMITTED | lead_auditor / auditor | Тайлан (≥1) + Excel хөтөлбөр (≥1) байх; холбогдох файл/линк сонголтоор | v1 хадгалагдана, AI review эхэлнэ, захиралд мэдэгдэл |
| SUBMITTED → CAE_REVIEW | систем | AI review `done` | — |
| CAE_REVIEW → RETURNED | **зөвхөн cae** | Бүх AI санал шийдвэрлэгдсэн (APPROVED/EDITED/REJECTED) байх; эсвэл захирал «шийдвэрлээгүйг хасах»-ыг баталгаажуулах | `feedback_v{n}.json` царцаагдана, илгээсэн аудитор + багт мэдэгдэл |
| RETURNED → RESUBMITTED | багийн гишүүн | Шинэ тайлангийн файл/линк оруулах (заавал); Excel өөрчлөгдөөгүй бол өмнөхийг дахин ашиглана | v{n+1}, M14 recheck зөвхөн release хийгдсэн feedback-ийн эсрэг |
| CAE_REVIEW → APPROVED_FINAL | **зөвхөн cae** | Сүүлийн verdict READY / READY_WITH_FIXES, R1 = 0 (одоогийн `/finalize` дүрэм) | RPT дугаар, архив, бүх зүйл read-only |
| Аль ч төлөв → CANCELLED | cae / admin | Тайлбар заавал | Логт үлдэнэ |

- 3-аас олон давталт бол одоогийн `cycle_warning`-ийг захиралд харуул.
- Шилжилт бүрийг серверт шалга. Буруу төлөвөөс дуудвал `409` + Монгол тайлбар буцаа.

## 5. Харагдах байдлын хатуу дүрэм (хамгийн чухал)

Аудитор / ахлах аудитор `workflow ∈ {SUBMITTED, CAE_REVIEW}` үед зөвхөн дараахыг харна: аудитын нэр, код, илгээсэн огноо, хувилбарын дугаар, «Захирлын хяналтад» гэсэн төлөв, өөрийн оруулсан файлын жагсаалт.

Тэд дараахыг **харахгүй**: AI санал, verdict, R1–R4 тоо, захирлын шийдвэр, тэмдэглэл, `events`-ийн агуулга, review_report, экспорт.

- Хязгаарлалтыг **сервер талд** нэг газар хий: `visibleTo(session, job)` функц. Бүх endpoint үүнийг дуудна: `GET /jobs`, `GET /jobs/:id`, `/output/*`, `/export/*`, `/document`, `/sources*`, `/previous`, `/docs-prep`. UI-д нуух нь хангалтгүй.
- RETURNED болсны дараа аудитор **зөвхөн** `feedback_v{n}.json`-д царцсан зүйлийг харна:
  - APPROVED болон EDITED санал (EDITED бол захирлын засварласан текст), MAN-xxx тэмдэглэл;
  - REJECTED санал **харагдахгүй**;
  - AI-ийн дотоод confidence, rule ID-г нуух эсэхийг надаас асуу.
- Release-ээс хойш захирал шийдвэрээ өөрчилбөл тэр нь дараагийн хувилбарт л хамаарна. Илгээгдсэн feedback өөрчлөгдөхгүй.

## 6. Хувилбарлах (version)

Илгээлт бүр = нэг хувилбар: v1 = анхны илгээлт, v2 = эхний засвар гэх мэт. Одоогийн `C1, C2` дугаарлалттай уялдуул (`v{n}` = `C{n}`).

Хувилбар бүрт хадгалах зүйлс:

- Эх файлууд нь яг оруулсан хэлбэрээрээ, sha256-тай, өөрчлөгдөхгүй. Одоогийн `originals.js` + `originals/C{n}/` бүтцийг ашигла.
- **Google Docs / Drive линк** бол илгээх агшинд `.docx` хуулбар татаж (`server/fetch_url.js`-ийн одоогийн аргаар) тухайн хувилбарт эх файл болгон хадгална. Линк, татсан огноо, sha256-ийг тэмдэглэнэ. Татаж чадахгүй бол (эрх, нэвтрэлт) илгээлтийг зогсоож, «Файл → Download → .docx хийгээд оруулна уу» гэж хэл.
- Мета: хэн, хэзээ оруулсан, аудиторын «юу зассан» тайлбар (RESUBMIT үед заавал, ≤ 2000 тэмдэгт).
- Хувилбар хооронд тайлангийн текстийн ялгаа (догол мөрийн түвшинд, нэмэгдсэн/хасагдсан) харуулах — захиралд л.
- Хувилбар **устгагдахгүй**. Job 7 хоногийн retention нь эх файлыг устгадаг тул `workflow ≠ APPROVED_FINAL` байх хугацаанд эх файлуудыг устгахгүй байх (эсвэл хувилбарын хавтсыг retention-оос чөлөөлөх) шийдлийг санал болго.

## 7. Мэдэгдэл ба эцсийн тайлан

**Мэдэгдэл.** Анхдагчаар вэб дотор мэдэгдэл: header-т хонх, тоо харагдана; `notifications.jsonl` хэрэглэгч бүрээр.

| Үйл явдал | Хэнд |
|---|---|
| SUBMITTED / RESUBMITTED | cae |
| RETURNED | илгээсэн аудитор + team |
| APPROVED_FINAL | team |

Имэйл (SMTP) хэрэгтэй эсэхийг надаас асуу; хэрэгтэй бол тохиргоог `config/`-д, нууц үгийг EFS-тэй файлд хадгал.

**Эцсийн тайлан (зөвхөн захирал).** APPROVED_FINAL болсны дараа «Эцсийн тайлан татах» товч гарна:

1. Аудиторын **сүүлийн хувилбарын** тайлан, эх хэлбэрээр (.docx).
2. Ижил тайлангийн PDF хувилбар (одоогийн Edge/Chrome PDF аргаар). Нүүрэнд RPT дугаар, батлагдсан огноо, батлагчийн нэр байна.
3. «Бүх хувилбар + хяналтын түүх» ZIP: v1…vn эх файл, feedback бүр, approval.json.

Татах бүрийг `auditLog('final.download')`-д бүртгэ.

## 8. Ажлын дараалал

1. **Төлөвлөгөө.** Өөрчлөх файлууд, шинэ endpoint (`POST /jobs/:id/submit`, `/release`, `/resubmit`, `GET /notifications`, `/final`), `job.json`-ийн шинэ талбаруудыг надад харуулаад зөвшөөрөл ав.
2. `users.js`: role, PERMS, team.
3. `server.js`: `workflow` төлөвийн машин + `visibleTo()` + хуучин job-ийн migration (`workflow` байхгүй бол: finalized → APPROVED_FINAL, done → CAE_REVIEW).
4. Release + `feedback_v{n}.json` + мэдэгдэл.
5. Хувилбарлалт, Google линкийн хуулбар, retention-ийн өөрчлөлт.
6. `web/index.html`: role тус бүрийн дэлгэц.
   - Аудитор: «Миний хүсэлтүүд» + төлөв.
   - Захирал: «Хяналт хүлээж буй» дараалал + «Батлаад илгээх» (баталгаажуулах цонхтой: «N санал аудиторт илгээгдэнэ, M татгалзсан»).
   - Хувилбарын timeline.
7. `docs/openapi.yaml`, `README.md`, `CLAUDE.md`-г шинэчил.
8. Тест (`node --test` эсвэл одоогийн тестийн арга). Доорх шалгуур бүрт нэг тест.

## 10. Эхлэхээс өмнө надаас асуух зүйлс

1. Ахлах аудитор багийн бусад аудиторын илгээлтийг баталж (дотоод хяналт) байж захиралд очих уу, эсвэл шууд захиралд очих уу?
2. Аудиторт AI-ийн rule ID / confidence харагдах уу, эсвэл зөвхөн засах зүйлийн текст үү?
3. Имэйл мэдэгдэл хэрэгтэй юу (SMTP сервер байгаа юу)?
4. Эцсийн тайлан .docx-ээс гадна Google Docs дээрх эх хувилбарт «Батлагдсан» тэмдэг тавих шаардлагатай юу?
